# Battle rendering performance

The battle renderer is primarily limited by GPU submissions and pixel work on slower devices. In an iPhone-sized Chromium software-WebGL profile with a seven-entity battle, the original scene used 186 draw calls. Batching repeated scenery images and animated river waves, and caching the static sun shadow map, reduced the same light scene to about 100 draw calls. The exact number varies as troops and effects enter the battle.

The renderer starts at the device's normal pixel density, capped at 2. During an active battle, three consecutive one-second samples below 42 FPS lower its rendering resolution. A severe result below 22 FPS selects the minimum in one resize, avoiding repeated canvas reallocations. Eight samples above 52 FPS allow resolution to recover. The HTML controls remain at their native screen resolution. Pauses, the lobby, and the opening animation do not drive this governor.

To repeat the Chromium profile locally, start the Vite server on port 5188, then run `node scripts/profile-runtime.mjs --phone` (or omit `--phone` for desktop). The script waits for native animation assets to load and reports rendered frames, draw calls, pixel ratio, main-thread cost, and JavaScript samples. Software WebGL and the automatic AI battle make FPS figures variable; draw calls and sustained frame cost are the more stable comparisons. `tests/browser/render-performance.spec.ts` checks the full scene on desktop, mobile Chrome, and mobile Safari.

For a crowded fight, run `node scripts/profile-runtime.mjs --stress --phone --swarms=8 --ratio=1`. The deterministic fixture holds eight Skeleton Army deployments (120 troops plus six towers) on screen. Add `--no-batch` for the unbatched comparison. On the same phone-sized software-WebGL setup, batching identical unfiltered animation frames reduced draw calls from about 696 to 460 and the median JavaScript frame callback from about 5.3 ms to 3.9 ms. The batched and unbatched frames are pixel-identical in mobile Chrome and Safari regression checks. FPS remains variable in software WebGL; a 25-second batched run held roughly 460 draw calls and 508 GPU geometries, versus 488 after six seconds. Inactive batch buffers are released after 120 frames, and a new battle clears the pool.

To measure combat CPU cost separately, run `node scripts/profile-engine.mjs`. It holds 120 troops alive and forces them to reacquire targets on every tick, representing a worst-case churn rather than a normal match. Replacing per-troop candidate arrays and sorting with a stable single scan reduced the median of five 300-step samples from 384 ms to 160 ms on this development machine, with the same final target checksum. Existing replay tests cover saved battle behavior.

Collision separation now rejects impossible overlaps along either axis before calculating a full distance. `node scripts/profile-engine.mjs --collisions` isolates that work; add `--reference=eccdaa5` to build the committed pre-optimization engine without changing worktree files. Distance instrumentation runs separately from the five timing samples. Over 300 updates of the same 126-entity fixture, full-distance calls fall from 2,358,000 to 96,222 (95.9%), with identical entity SHA-256 hashes. Two local before/after runs measured median collision times of 76/47 ms and 85/23 ms; the timing variation limits generalization. A full-battle sample measured 275/235 ms, also with identical entity hashes. These are local CPU observations, not physical-device FPS or battery measurements. The original contact arithmetic and pair order remain intact; 220 position checkpoints independently captured from the old engine and complete historical matches guard replay behavior.

The stress fixture and runtime profiler wait for all arena libraries to finish their rebuild and paint before sampling, rather than treating the animation-file count alone as a rendered-native-scene signal. Current desktop batched/unbatched sprites remain byte-identical. Phone WebKit produces thirteen one-level pixel differences in a 258,960-pixel frame; the current comparison bounds differences to one channel level and fewer than 0.01% of pixels, while retaining desktop byte equality. Each comparison attaches both source images. Ground-marker overlap retains its separate 3% bound.

The remaining small 3D sparks now share one instanced mesh. Run `ARENA_PROFILE_SECONDS=1 node scripts/profile-runtime.mjs --stress --phone --swarms=0 --crowns=3 --ratio=1 --fixed-time=3` to reproduce the three-crown fixture. It retains all 72 sparks while reducing the frame from 174 to 103 draws and from 132 to 61 GPU geometries. A controlled before/after screenshot comparison was pixel-identical; the mobile Chrome and Safari browser checks guard the draw count. The mesh is hidden when the effect ends and disposed when the battle resets.

Ground shadows and team rings now share geometries and materials, then render as three instanced meshes in large battles. The 126-entity phone stress fixture falls from 460 to 105 draw calls and from 301 to 63 GPU geometries. Median JavaScript frame cost fell from 3.7 to 1.4 ms in the fixed-time profile. Transparent marker overlaps differ slightly in the shared draw; the screenshot check bounds those differences to 3% of pixels on desktop Chrome, phone Chrome, and phone Safari. Small battles keep their individual marker draws.

The 49 animation families reference 49 texture atlases, but five pairs have identical image bytes. The loader now shares the pending request and resulting texture for each pair, so the full animation gallery makes 44 atlas requests and retains 44 texture objects. The eliminated duplicates represent 6.5 MB of compressed image references and 56 MiB at uncompressed RGBA dimensions; actual browser memory savings depend on which atlases are decoded and uploaded. The importer regenerates the short alias map from verified texture hashes, and the asset test checks that every alias remains byte-identical to its source.

The full offline pack lists 921 URLs, about 108 MB before deduplication. Twenty-seven of those URLs have byte-identical files; the service worker fetches and stores one response per content hash and file type, leaving 894 unique entries and omitting 8.1 MB of duplicate bytes on a new install. It keys responses by content hash and copies unchanged bytes from the prior release on update, even if the canonical URL has changed. It verifies the hashes of older unversioned cache entries during the first migration. A new install fetches at most 24 unique offline files at once, and the worker still becomes active only after the complete pack is cached. `npm run test:cache-upgrade` verifies legacy and versioned upgrades, duplicate URLs, and offline aliases; `npm run test:offline` exercises a full production offline battle.

Native SVG UI rendering now shares each repeated polygon's fitted image markup within a single render call. Filtered pieces also reuse that image rather than performing the same affine fit twice. The cache contains no per-instance clip/filter IDs or color state and does not survive the call, so resized or replaced geometry is still recalculated. An instrumented comparison with `22d054c` covers 17,502 frame/options cases across nine native UI datasets and all 74 card portraits. Texture fits fall from 191,700 to 125,098, about 35%, with byte-identical SVG and accessible labels. Virtual shape bindings receive deterministic retained native shapes, and the Node comparison disables text fitting; browser checks retain actual bindings and font fitting. These are work counts, not frame-rate measurements.

Locally paused, unfinished battles and replays now retain their settled canvas instead of repeating the arena update and draw path. Scene replacement, resize, placement changes, reduced-motion changes, context restoration and page resume request a repaint. Asset loading keeps its existing draw cadence until the arena libraries finish and replace fallbacks. The main frame loop continues UI/audio/connection housekeeping. It keeps presentation timestamps current during idle frames so resuming does not age effects by the paused wall time.

An instrumented paused replay at 900 × 700 produced 72 repeated renders and 7,272 draw calls while its pixels and match clock stayed identical. The production probe now records zero additional renders over three seconds, unchanged game state, retained pixels identical to a forced fresh repaint, and zero presentation-time advance while paused. These are work counts, not an FPS or battery-life guarantee. Main-thread timings vary by host and build mode.

Run `node scripts/profile-paused.mjs` against a server on port 5188 to repeat the fixed replay sample; `ARENA_PROFILE_URL` and `ARENA_PROFILE_SECONDS` change its target and duration. It uses a separate browser profile, verifies canvas retention and page-resume repaint, and reports effect/match time after replay resume. It also works against a production preview. `paused-rendering.spec.ts` checks both replay perspectives, resize, reduced motion, page resume, seeks, delayed native artwork, solo placement cleanup and resumption on desktop Chromium and phone WebKit. Real context-recovery and pause-result checks cover the graphics and ending transitions.

The paused UI probe also counts body-wide DOM mutations. One three-second sample produced 1,324 mutations, all restoring unchanged values: hidden announcement/intro classes, hand labels and datasets, next-card attributes, replay text and graphics-warning visibility. Shared text/attribute setters compare the current DOM value before writing; graphics/hand disabled states and inactive overlay classes receive the same guards. The matched production sample records zero mutations, zero arena redraws and unchanged game/canvas state. These counts describe avoided DOM work rather than a frame-rate or battery-life result.

The paused-replay browser checks require zero subtree mutations after native UI loading settles, then verify that seeking updates the clock and accessibility text. An unavailable Mirror retains its disabled state and unknown cost without repeated writes. Card selection/deployment, changing Mirror costs, timer layouts, native intros/notices and real context recovery still update through their normal loops.

Lobby dialogs also retain the arena canvas after its requested paint. Late assets, viewport changes, reduced-motion changes, page restoration and graphics recovery request a new paint at the held ambient pose. Closing the dialog resumes the lobby animation. The frame loop continues input, UI, networking and lifecycle work while the canvas rests; active multiplayer matches and completed-match effects keep their existing rendering behavior.

To repeat the covered-lobby comparison, start Vite or a production preview on port 5188 and run `node scripts/profile-modal.mjs`. The probe waits for artwork, opens card details, samples three seconds, compares game state and canvas pixels, requests a page-restoration paint and closes the dialog. `ARENA_PROFILE_URL` and `ARENA_PROFILE_SECONDS` override the URL and sample duration. On the same 900 × 700 Chromium software-WebGL setup, the earlier loop rendered 18 frames at 96 draw calls each; the retained loop rendered zero frames during the sample, held the same pixels and clocks, reproduced the pixels after restoration, and resumed rendering on close. This measures avoided arena submissions, rather than physical phone FPS or battery life.

Collection search, type/cost filtering and sorting reuse each card row and its native SVG within the current collection grid. A weak map associates the row cache with that grid, retaining at most one row per roster card for its lifetime. A read-only card inspection retains its parent builder until Back restores it or the inspector closes. Otherwise, replacing or closing the dialog permits the old grid/cache to be collected; a new builder draws fresh deck membership and labels. Hidden rows receive normal native hydration when shown again, including artwork that arrived while they were detached. Identical result orders skip child replacement, and unchanged result/mode labels skip DOM writes.

Run `node scripts/profile-collection.mjs` against a server on port 5188 to reproduce the collection comparison (`ARENA_PROFILE_URL` overrides the URL). It waits for artwork, opens the collection and enters `g`, `go`, `gob`, `goblin`, then clears the search. On matching 900 × 700 production Chromium runs, the earlier implementation rebuilt 118 native SVGs and retained none of the original card/SVG objects. The cached implementation rebuilt zero and retained all 74. Both restore the same 14,216 collection DOM nodes and identical final dialog pixels, with zero arena redraws during the interaction. These counts describe avoided SVG construction; automated fill times and software rendering are not a physical-device responsiveness or memory measurement.

Add `--types` to click Troops, Spells, Buildings and All cards. The earlier type handlers rebuilt the dialog four times and reconstructed 148 collection SVGs, replacing every original card/SVG object. Updating the active class and `aria-pressed` flags in place, then rendering the cached grid, reduces both counts to zero and retains all 74 card/SVG objects. The same production comparison preserves the final dialog pixels, 14,216 visible collection nodes and zero arena redraws. Search, cost, sort, selected deck slot and control focus retain their existing state.

Add `--inspect` to open Musketeer details and return to the collection. The earlier Back handler reconstructed all 74 collection SVGs and replaced every card element. Retaining the read-only parent builder reduces collection SVG construction to zero and restores all original card/SVG objects. Both versions perform the two ordinary view swaps and retain 14,216 collection nodes, with zero arena redraws during the interaction. Back restores the clicked card's focus and saved collection scroll; closing the inspector releases its parent callback instead of accumulating old views. Native artwork that arrives while the builder is detached is hydrated when it returns.


Hand refreshes now retain unchanged slots, including forced refreshes after deployment. Run `node scripts/profile-hand.mjs` against Vite or production preview on port 5188 to reproduce a real Skeletons play from a fixed cheap deck. On matching 900 × 700 production Chromium runs, the earlier hand rebuilt the three unchanged native SVGs and retained none of their buttons or SVG objects. Reconciliation reduces unchanged SVG construction to zero and retains all three buttons/SVGs. Both runs have one root mutation, one accepted action, the same resulting hand and 384 hand descendants. The newly drawn card keeps its normal authored reveal. These are avoided-construction and object-identity counts, not physical-device timing or process-memory measurements.

Add `--selection` for ten cycles of selecting/deselecting Skeletons. The probe tracks newly encountered SVG objects, distinguishing construction from reattachment. Before static-view caching, 20 new SVGs are constructed and the original normal SVG is replaced. With the cache, only the first selected view is constructed and the original normal SVG returns; both runs keep the same hand, zero blue deployments and 384 mounted hand descendants. A host can retain one additional detached static view; this trades bounded DOM retention for avoided reconstruction. The measurements do not establish physical-device latency or process-memory improvements. Set `ARENA_PROFILE_ARTIFACTS` to a local directory to retain optional before/after card captures and raw pixel-difference counts.

Add `--idle` to inspect three seconds of an active battle without selecting a card. The probe temporarily counts the native hand's exact DOM query and restores the original query method afterward. A production Chromium baseline performs 34 full-hand scans during 18 rendered frames; the guarded run performs 15 during 19 frames. Both construct no SVGs, retain the same hand and 384 mounted descendants, and report no page errors. The guard removes the extra animation-loop scan when no reveal is visible, and skips duplicate scans at the same simulation time. HUD refreshes still update costs, selection and labels. These are avoided query/check counts; the small frame-count difference in software rendering is not evidence of a physical-device speedup.

## Native evidence harness

The shared Unicorn harness caches accepted instruction-range decisions, defers unused stack reads and registers fixed callbacks at their handled addresses. The global instruction gate remains active for every instruction, with the same pinned binary, memory protections, instruction budgets and contextual callback checks. Only declared range extension is exposed; accepted addresses remain valid, and rejected addresses are not cached.

A matching serial `--sight-range --primary-acquisition --target-eligibility --check` retains identical 2,704 cases, 84 controls, two self controls and nineteen blocks. One local before/after pair measures 92.882 → 22.579 wall seconds and 91.884 → 21.707 user CPU seconds, about 4.1× faster verification. These are development-tool measurements, not game frame rate or device latency. `python3 scripts/check-instruction-ranges.py` separately compares 49,832 cold/hot admission decisions with the original definition across twelve extension stages, including half-open endpoints, overlaps, gaps, reversed/empty ranges and rejected-then-added addresses.
