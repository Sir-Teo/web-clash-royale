# Battle rendering performance

The battle renderer is primarily limited by GPU submissions and pixel work on slower devices. In an iPhone-sized Chromium software-WebGL profile with a seven-entity battle, the original scene used 186 draw calls. Batching repeated scenery images and animated river waves, and caching the static sun shadow map, reduced the same light scene to about 100 draw calls. The exact number varies as troops and effects enter the battle.

The renderer starts at the device's normal pixel density, capped at 2. During an active battle, three consecutive one-second samples below 42 FPS lower its rendering resolution. A severe result below 22 FPS selects the minimum in one resize, avoiding repeated canvas reallocations. Eight samples above 52 FPS allow resolution to recover. The HTML controls remain at their native screen resolution. Pauses, the lobby, and the opening animation do not drive this governor.

To repeat the Chromium profile locally, start the Vite server on port 5188, then run `node scripts/profile-runtime.mjs --phone` (or omit `--phone` for desktop). The script waits for native animation assets to load and reports rendered frames, draw calls, pixel ratio, main-thread cost, and JavaScript samples. Software WebGL and the automatic AI battle make FPS figures variable; draw calls and sustained frame cost are the more stable comparisons. `tests/browser/render-performance.spec.ts` checks the full scene on desktop, mobile Chrome, and mobile Safari.

For a crowded fight, run `node scripts/profile-runtime.mjs --stress --phone --swarms=8 --ratio=1`. The deterministic fixture holds eight Skeleton Army deployments (120 troops plus six towers) on screen. Add `--no-batch` for the unbatched comparison. On the same phone-sized software-WebGL setup, batching identical unfiltered animation frames reduced draw calls from about 696 to 460 and the median JavaScript frame callback from about 5.3 ms to 3.9 ms. The batched and unbatched frames are pixel-identical in mobile Chrome and Safari regression checks. FPS remains variable in software WebGL; a 25-second batched run held roughly 460 draw calls and 508 GPU geometries, versus 488 after six seconds. Inactive batch buffers are released after 120 frames, and a new battle clears the pool.

To measure combat CPU cost separately, run `node scripts/profile-engine.mjs`. It holds 120 troops alive and forces them to reacquire targets on every tick, representing a worst-case churn rather than a normal match. Replacing per-troop candidate arrays and sorting with a stable single scan reduced the median of five 300-step samples from 384 ms to 160 ms on this development machine, with the same final target checksum. Existing replay tests cover saved battle behavior.

The remaining small 3D sparks now share one instanced mesh. Run `ARENA_PROFILE_SECONDS=1 node scripts/profile-runtime.mjs --stress --phone --swarms=0 --crowns=3 --ratio=1 --fixed-time=3` to reproduce the three-crown fixture. It retains all 72 sparks while reducing the frame from 174 to 103 draws and from 132 to 61 GPU geometries. A controlled before/after screenshot comparison was pixel-identical; the mobile Chrome and Safari browser checks guard the draw count. The mesh is hidden when the effect ends and disposed when the battle resets.

Ground shadows and team rings now share geometries and materials, then render as three instanced meshes in large battles. The 126-entity phone stress fixture falls from 460 to 105 draw calls and from 301 to 63 GPU geometries. Median JavaScript frame cost fell from 3.7 to 1.4 ms in the fixed-time profile. Transparent marker overlaps differ slightly in the shared draw; the screenshot check bounds those differences to 3% of pixels on desktop Chrome, phone Chrome, and phone Safari. Small battles keep their individual marker draws.

The 49 animation families reference 49 texture atlases, but five pairs have identical image bytes. The loader now shares the pending request and resulting texture for each pair, so the full animation gallery makes 44 atlas requests and retains 44 texture objects. The eliminated duplicates represent 6.5 MB of compressed image references and 56 MiB at uncompressed RGBA dimensions; actual browser memory savings depend on which atlases are decoded and uploaded. The importer regenerates the short alias map from verified texture hashes, and the asset test checks that every alias remains byte-identical to its source.

The full offline pack lists 921 URLs, about 108 MB before deduplication. Twenty-seven of those URLs have byte-identical files; the service worker fetches and stores one response per content hash and file type, leaving 894 unique entries and omitting 8.1 MB of duplicate bytes on a new install. It keys responses by content hash and copies unchanged bytes from the prior release on update, even if the canonical URL has changed. It verifies the hashes of older unversioned cache entries during the first migration. A new install fetches at most 24 unique offline files at once, and the worker still becomes active only after the complete pack is cached. `npm run test:cache-upgrade` verifies legacy and versioned upgrades, duplicate URLs, and offline aliases; `npm run test:offline` exercises a full production offline battle.

Native SVG UI rendering now shares each repeated polygon's fitted image markup within a single render call. Filtered pieces also reuse that image rather than performing the same affine fit twice. The cache contains no per-instance clip/filter IDs or color state and does not survive the call, so resized or replaced geometry is still recalculated. An instrumented comparison with `22d054c` covers 17,502 frame/options cases across nine native UI datasets and all 74 card portraits. Texture fits fall from 191,700 to 125,098, about 35%, with byte-identical SVG and accessible labels. Virtual shape bindings receive deterministic retained native shapes, and the Node comparison disables text fitting; browser checks retain actual bindings and font fitting. These are work counts, not frame-rate measurements.

Locally paused, unfinished battles and replays now retain their settled canvas instead of repeating the arena update and draw path. Scene replacement, resize, placement changes, reduced-motion changes, context restoration and page resume request a repaint. Asset loading keeps its existing draw cadence until the arena libraries finish and replace fallbacks. The main frame loop continues UI/audio/connection housekeeping. It keeps presentation timestamps current during idle frames so resuming does not age effects by the paused wall time.

An instrumented paused replay at 900 × 700 produced 72 repeated renders and 7,272 draw calls while its pixels and match clock stayed identical. The production probe now records zero additional renders over three seconds, unchanged game state, retained pixels identical to a forced fresh repaint, and zero presentation-time advance while paused. These are work counts, not an FPS or battery-life guarantee. Main-thread timings vary by host and build mode.

Run `node scripts/profile-paused.mjs` against a server on port 5188 to repeat the fixed replay sample; `ARENA_PROFILE_URL` and `ARENA_PROFILE_SECONDS` change its target and duration. It uses a separate browser profile, verifies canvas retention and page-resume repaint, and reports effect/match time after replay resume. It also works against a production preview. `paused-rendering.spec.ts` checks both replay perspectives, resize, reduced motion, page resume, seeks, delayed native artwork, solo placement cleanup and resumption on desktop Chromium and phone WebKit. Real context-recovery and pause-result checks cover the graphics and ending transitions.
