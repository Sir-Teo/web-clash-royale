# Battle rendering performance

The battle renderer is primarily limited by GPU submissions and pixel work on slower devices. In an iPhone-sized Chromium software-WebGL profile with a seven-entity battle, the original scene used 186 draw calls. Batching repeated scenery images and animated river waves, and caching the static sun shadow map, reduced the same light scene to about 100 draw calls. The exact number varies as troops and effects enter the battle.

The renderer starts at the device's normal pixel density, capped at 2. During an active battle, three consecutive one-second samples below 42 FPS lower its rendering resolution. A severe result below 22 FPS selects the minimum in one resize, avoiding repeated canvas reallocations. Eight samples above 52 FPS allow resolution to recover. The HTML controls remain at their native screen resolution. Pauses, the lobby, and the opening animation do not drive this governor.

To repeat the Chromium profile locally, start the Vite server on port 5188, then run `node scripts/profile-runtime.mjs --phone` (or omit `--phone` for desktop). The script waits for native animation assets to load and reports rendered frames, draw calls, pixel ratio, main-thread cost, and JavaScript samples. Software WebGL and the automatic AI battle make FPS figures variable; draw calls and sustained frame cost are the more stable comparisons. `tests/browser/render-performance.spec.ts` checks the full scene on desktop, mobile Chrome, and mobile Safari.

For a crowded fight, run `node scripts/profile-runtime.mjs --stress --phone --swarms=8 --ratio=1`. The deterministic fixture holds eight Skeleton Army deployments (120 troops plus six towers) on screen. Add `--no-batch` for the unbatched comparison. On the same phone-sized software-WebGL setup, batching identical unfiltered animation frames reduced draw calls from about 696 to 460 and the median JavaScript frame callback from about 5.3 ms to 3.9 ms. The batched and unbatched frames are pixel-identical in mobile Chrome and Safari regression checks. FPS remains variable in software WebGL; a 25-second batched run held roughly 460 draw calls and 508 GPU geometries, versus 488 after six seconds. Inactive batch buffers are released after 120 frames, and a new battle clears the pool.

To measure combat CPU cost separately, run `node scripts/profile-engine.mjs`. It holds 120 troops alive and forces them to reacquire targets on every tick, representing a worst-case churn rather than a normal match. Replacing per-troop candidate arrays and sorting with a stable single scan reduced the median of five 300-step samples from 384 ms to 160 ms on this development machine, with the same final target checksum. Existing replay tests cover saved battle behavior.

The remaining small 3D sparks now share one instanced mesh. Run `ARENA_PROFILE_SECONDS=1 node scripts/profile-runtime.mjs --stress --phone --swarms=0 --crowns=3 --ratio=1 --fixed-time=3` to reproduce the three-crown fixture. It retains all 72 sparks while reducing the frame from 174 to 103 draws and from 132 to 61 GPU geometries. A controlled before/after screenshot comparison was pixel-identical; the mobile Chrome and Safari browser checks guard the draw count. The mesh is hidden when the effect ends and disposed when the battle resets.

The full offline pack contains 921 files, about 108 MB. The service worker now keys each cached file by its content hash and copies unchanged responses from the prior release on update. It verifies the hashes of older unversioned cache entries during the first migration. An unchanged arena asset is not downloaded again just because the app code changed. A new install fetches at most 24 offline files at once, and the worker still becomes active only after the complete pack is cached. `npm run test:cache-upgrade` verifies legacy and versioned upgrades by changing one file at a time; `npm run test:offline` exercises a full production offline battle.
